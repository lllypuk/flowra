# Минимум инфраструктуры: что убирается дёшево и какие нужны замеры

Разбор по задаче лида T-0012, 12.11.2026. Авторы: Claude (сессия Flowra) и Codex (правая панель).
Продуктовый код не менялся; код замеров — `tests/load/agentbench`. Где не сошлись, записаны обе позиции
(раздел 7). Цены — оценки Claude в днях работы агента, не замеры.

Вводная владельца: «если можно обойтись минимумом инфраструктуры, то лучше двигаться в эту сторону,
чтобы было меньше зависимостей; сервис — на одного человека и агентов, максимум небольшая команда людей
и большое количество агентов» и «с SQLite нужны будут замеры, без этого на неё точно не надо съезжать,
может, и Монги будет норм для гибкости».

## 1. Опись

Что надо поднять с нуля, чтобы работали лента и чат-задачи (ветка `plan/leadfeed-readonly-slice`,
режим `auth.mode: token`).

| Что | Память в покое | Зачем продукту | Что без него |
|---|---|---|---|
| MongoDB 6, один узел replica set | 116–135 МБ, образ 801 МБ | event store чатов и публикация ленты идут транзакциями; read models, сообщения, пользователи, outbox | не работает ничего |
| `mongo-init`, разовый контейнер | — | один раз вызывает `rs.initiate` | транзакции не работают: нет replica set |
| Redis 7 | 9–11 МБ, образ 40 МБ | шина событий (pub/sub), очередь недоставленных событий; хранилище токенов — только в режиме Keycloak | API не стартует: клиент Redis обязателен при запуске |
| Процесс API | 32–35 МБ | HTTP, WebSocket, обработчики шины | — |
| Процесс воркера | 29 МБ | переносит события из outbox в шину, чинит проекции, синхронизирует пользователей из Keycloak | события чатов не доходят до шины; лента работает |
| `bin/leadfeed` по таймеру, `lead-task export` | пик 20 МБ на 0,04 с | наполняют ленту | лента не обновляется |
| Keycloak и его Postgres | около 770 МБ | вход | в режиме токена не поднимаются; нужны только `docker-compose.prod.yml` |
| Docker | — | способ поднять Mongo и Redis; тесты `internal/infrastructure/**` и `tests/**` поднимают контейнеры через testcontainers | — |

Итого сейчас: два постоянных контейнера, два процесса, около 210 МБ в покое.

Что читает шину (поправка Codex: потребителей четыре, не три):

- проекция `tasks_read_model` (`cmd/api/container.go:818`) — без доставки `chat.*` список задач устаревает;
  синхронно обновляется только `chats_read_model`;
- уведомления и журналирование (`internal/infrastructure/eventbus/handlers.go:607`);
- рассылка в WebSocket (`internal/infrastructure/websocket/broadcaster.go:125`).

Чего шина не гарантирует уже сейчас: outbox помечает событие обработанным после `Publish` в Redis, а не
после работы обработчиков (`internal/worker/outbox_worker.go:218`); pub/sub Redis не хранит сообщения для
отсутствующего подписчика; подключения очереди недоставленных к обработчикам, исчерпавшим повторы, Codex
не нашёл.

Вне Mongo лежат загруженные файлы (`uploads`).

Codex: дешёвый опыт, а не доказанная экономия |

## 3. Профиль нагрузки

Все числа — предложение Claude, не замер использования; Codex считает их гипотезами, пока нет данных о
доле времени под нагрузкой и длине всплесков. Три режима вместо одного числа:

| Режим | Пишущих агентов | Темп | Комментарий |
|---|---|---|---|
| Обычный день | 10–15 (лид, сессии проектов, их Codex, 3–5 воркеров) | один отчёт или сообщение в минуты; за год порядка 250 тыс. сообщений, 5 тыс. задач | в среднем сотые доли записи в секунду |
| Активный пик | 50 | запись раз в 10 с у каждого, 5 записей/с, всплесками по минутам | несколько прогонов одновременно |
| Стресс | 100 | запись в секунду у каждого, 100 записей/с | запас, а не ожидание |

- Запись: 90% — сообщение в тред, 10% — изменение поля задачи.
- Тред: обычно 10–50 записей, длинный — до 2000. Тело 0,5–5 КБ; больше 10 000 байт HTTP не примет
  (`internal/handler/http/message_handler.go:20`) — длинное идёт вложением.
- Чтение: владелец и телефон опрашивают список раз в 15–60 с; агент при старте и после сжатия контекста
  читает задачу и страницу треда. Единицы запросов в секунду.

Что в этом профиле важнее пропускной способности (Codex, Claude согласен): конкуренция за одну горячую
задачу, корректность итога, повторы и идемпотентность, хвост задержек. Отдельно — длина потока событий
`chat.*`: проектор задач перечитывает весь поток агрегата на каждое событие
(`internal/infrastructure/projector/chat_to_task_read_model_projector.go:114`), и эту цену легко принять
за предел Mongo.

## 4. Базовая линия

Метод: `tests/load/agentbench/run.sh`, коммит `8284f53`. Свои MongoDB 6.0 (один узел replica set) и
Redis 7 в Docker на портах 27117 и 6479, один процесс API с `FLOWRA_WORKER=true` и входом по токену,
генератор ходит по HTTP с той же машины. Запись подтверждается настройками драйвера по умолчанию.
Тело сообщения 1 КБ, окна по 15 с, два прогона; диапазон — разброс между ними.

Сырые результаты — `docs/measurements/20261112-agentbench-run*.jsonl`. Это проба и база для проверки
корректности, а не эталон для сравнения движков. Границы цифр:

- Машина одна (16 ядер, 30 ГБ), генератор делит с сервером процессор, рядом шёл чужой прогон (средняя
  загрузка 7–39). Окна по 15 с, один-два прогона на точку.
- Замер уже снят в едином процессе: выигрыш от объединения воркера с API он не показывает.
- «Заданный темп» — не независимый поток запросов: агент ждёт ответа перед следующим, отставание от
  расписания в задержку не входит. Ошибки в перцентили не входят; ошибок и таймаутов не было.
- «Потолок» — предел связки «генератор + сервер + чужая нагрузка» на этой машине, не предел Mongo.
- Память Mongo и Redis снята `docker stats`, память API — RSS процесса: это разные способы учёта.
- Память и размер базы сняты после разного числа записей в разных прогонах; текст сообщений однообразен
  и сжимается лучше настоящего. Диск, пулы соединений, процессор и действующие настройки долговечности не
  записаны.

**Темп из профиля** (заданный темп, каждый агент в свой тред):

| Точка | Сообщение p95 / p99 | Изменение статуса p95 | Проверка итога |
|---|---|---|---|
| 50 агентов × 0,1/с, 74 операции за окно | 14–18 мс / 21 мс | 19–23 мс | последний запрошенный статус совпал во всех чатах |
| 100 агентов × 1/с, 1499 операций за окно 15 с | 23–25 мс / 40–44 мс | 34–40 мс | последний запрошенный статус совпал во всех чатах через 0,3–0,5 с после конца нагрузки |

Проверка итога слабая: сверяется только последнее значение каждого чата по `chats_read_model`, потеря
промежуточных изменений в ней не видна, а время — это ожидание после нагрузки, не задержка применения
каждого действия. Здесь каждый агент писал в свою задачу; общая задача — в разделе 5.

## 5. Что нашлось по корректности

Это не про инфраструктуру, но меняет порядок шагов.

**Изменения одной задачи теряются при ответе 200.** Сценарий: N агентов раз в секунду ставят одной общей
задаче уникальный срок; каждый принятый запрос обязан оставить событие `chat.due_date_set`.

| Агентов на одну задачу | Принято (HTTP 200) | Применено | Потеряно |
|---|---|---|---|
| 1 | 15 | 15 | 0 |
| 2 | 30 | 30 | 0 |
| 10 | 150 | 148 | 2 |
| 50 | 750 | 449 | 301 (40%) |

Это недостающие эффекты принятых запросов, а не потеря уже записанных данных Mongo. 301 — разность
между принятыми запросами и событиями; сверки значений срока с событиями не было, так что это нижняя
граница. В журнале API за сценарий — 3271 запись о конфликте версий и 688 записей с `WriteConflict`; это
число попыток, а не проигравших команд. Что видно в коде: тег исполняется в отвязанной горутине после
ответа (`internal/application/message/send_message.go:185`), повторов пять и до 3 с
(`internal/domain/tag/executor.go:21`). Вызывающий о потере не узнаёт. Один прогон.

Починка — не «повторять `WriteConflict`» (Codex, Claude согласен): запись событий уже идёт через
`WithTransaction`. Нужны определённый итог действия (зафиксировано с версией, отказ или неизвестный
исход), повтор доменной команды с перезагрузкой агрегата отдельно от повтора транзакции драйвером,
ограниченные повторы либо очередь на один агрегат, и ключ команды для повтора при неизвестном исходе.
После починки задержку ответа нельзя сравнивать с нынешней: подтверждение станет сильнее.

**Действие «переименовать» ничего не переименовывает.** `ActionService.Rename`
(`internal/service/action_service.go:260`) пишет в тред «title changed», но события `chat.renamed` нет и
имя чата прежнее. Проверено одним запросом.

## 6. Замеры для сравнения хранилищ

Сравнивать можно только одинаковое. Базовая линия раздела 4 — измерение продукта целиком: в ней сидят
горутины тегов, пересборка проекций, журнал, Redis. Цену Mongo она не выделяет.

Для сравнения движков нужен отдельный опыт: два адаптера под одни и те же операции и одни и те же данные.

- Операции: запись и изменение сообщения, страница треда по индексу; добавление событий агрегата с
  ожидаемой версией и чтение потока; запись и чтение одной представительной проекции; при желании —
  атомарная замена ленты с одновременным чтением.
- Сценарии: разные задачи одновременно, одна горячая задача, перезапуск, восстановление из копии.
- Одинаковыми должны быть границы транзакций, индексы, повторы и подтверждение записи. Нельзя дать
  встроенному хранилищу одну транзакцию на «событие + outbox» и сравнить с нынешним путём Mongo в
  несколько фиксаций: выиграет не движок.
- Долговечность: Mongo, один узел replica set, явное подтверждение majority с журналом — против SQLite
  WAL с `synchronous=FULL` на том же диске. `NORMAL` — отдельная строка с ослабленной гарантией, не
  заголовок. Ни то ни другое не отказоустойчивость.
- Сбои: `kill -9` проверяет падение процесса, а не питания. У Mongo падение API и падение хранилища — два
  случая, у встроенного хранилища — один; сравнивать их как одинаковые нельзя. После сбоя сверяются
  подтверждённые идентификаторы.
- Кроме скорости: память процесса и базы одним способом, размер на диске с журналами и индексами,
  холодный старт, согласованная резервная копия под записью и восстановление в новый каталог.
- Нагрузка заданным темпом, с числом выборок у каждого перцентиля, повторами и записанными версиями,
  конфигурацией, железом и диском.

Что это покажет и чего нет: пригодность движка в узкой области «сообщения и журнал событий». Проекции,
outbox, починка, запросы, пользователи и воркспейсы написаны под Mongo и остаются работой миграции;
`InMemoryEventStore` её не решает.

Цена:

| Что | Цена | Что даёт |
|---|---|---|
| Второе хранилище ленты за `Publisher` и `Reader` | 1–2 дня | самое дешёвое, но непоказательно: в ленту пишет один импортёр раз в минуту |
| Опыт на двух адаптерах (сообщения, журнал событий, одна проекция), нагрузка, сбои, отчёт | 5–8 дней, оценка Claude | честное сравнение движков в узкой области |
| Перевод продукта на встроенное хранилище | не оценивалось | — |

Codex числа в днях для опыта не даёт: без разложения объёма обоснованной оценки нет.

## 7. Рекомендация

Оба: Mongo пока остаётся. Встроенное хранилище — вариант, а не цель; заказывать опыт стоит только под
измеренное ограничение или цену эксплуатации, которые останутся после дешёвых шагов.

Порядок шагов, позиция Claude:

1. Единый процесс в `make dev-local` и опыт с кэшем Mongo: замер раздела 4 до и после. Итог: Mongo,
   Redis и один процесс.
2. Починить контракт записи (раздел 5) и повторить сценарий общей задачи. Без этого профиль «много
   пишущих агентов» упирается не в хранилище. Оценка Claude — 3–5 дней; шаг 1 его не задерживает.
3. Шина в памяти — если владельцу важен минус один контейнер. Итог: Mongo и один процесс.
4. Опыт с двумя адаптерами — если после шагов 1–3 остаётся названное ограничение. Сам опыт можно
   проектировать раньше, но сравнивать продукт целиком — только после шага 2.

Остановиться можно после любого шага. Codex с порядком согласен: шаг 2 раньше шины, «упрощённый Mongo и
один процесс API» — допустимый окончательный итог.

Что решает владелец:

1. Какой итог считать достаточным: «Mongo и один процесс» или продолжать до встроенного хранилища.
2. Нужен ли шаг 3: минус Redis ценой 3–5 дней.
3. Где и как это работает: Compose или пакеты под systemd; на ноутбуке или на постоянно включённой машине.
4. Бюджеты для сравнения: сколько памяти и диска допустимо, какая задержка заметна, сколько
   подтверждённых записей можно потерять при сбое и за какое время восстановиться.
5. Профиль нагрузки раздела 3: принять три режима или дать свои числа.
6. Будет ли небольшая команда людей: от этого зависит судьба кода Keycloak.
7. Сколько хранить переписку и вложения.

## 9. Итог шагов 1 и 2 (T-0013)

Решения владельца 12.11: «Mongo и один процесс» пока достаточно, Redis остаётся, код Keycloak выбрасывается
отдельной задачей, профиль раздела 3 принят. Ветка `fix/write-contract`, план —
`docs/plans/completed/20261112-write-contract.md`.

Keycloak удалён в ветке `feat/remove-keycloak`, план — `docs/plans/completed/20261112-remove-keycloak.md`; ниже
упоминания Keycloak и `make dev-local` описывают состояние на момент замеров.

**Шаг 1.** `make dev-local` запускает один процесс API с воркером внутри (`FLOWRA_WORKER=true`), отдельного
`cmd/worker` нет. `make dev` с Keycloak не менялся. Сам `make dev-local` не запускался: он поднимает Compose на
портах стека лида; режим тот же, что в замерах ниже.

**Шаг 2.** Действия (`/chats/:id/actions/*`, `/tasks/:task_id/actions/*`, `PUT /tasks/:task_id/...`) больше не
пишут сообщение с тегом, а применяют команду в запросе через `chatapp.CommandRunner`: блокировка на чат в
процессе, до 5 попыток с перезагрузкой агрегата при конфликте версий, `Idempotency-Key` пишется в последнее
событие команды той же транзакцией. Ответ: 200 с версией (или `replayed`), 409 — не применено, 503
`OUTCOME_UNKNOWN` — фиксация оборвалась, повторить с тем же ключом. `rename` переименовывает. Проекции
`chats_read_model` и `tasks_read_model` пишутся только с версией не старше записанной. Тег в тексте сообщения
остаётся после ответа и без итога — так и записано в `docs/api/action-endpoints.md` и `docs/TAGS_USER_GUIDE.md`.

Метод: `tests/load/agentbench/run.sh` с `BENCH_RUNS=3`, «до» — бинарь API ветки `analysis/min-infra` с тем же
генератором. Каждый запрос со своим ключом; сверка по Mongo через 8 с после нагрузки: каждый принятый срок —
ровно одним событием `chat.due_date_set`, отказанный — ни одним, чужих и двойных событий нет, `chats_read_model` и
`tasks_read_model` равны последнему событию. Сырые данные — `docs/measurements/20261112-write-contract-*.jsonl`.

Общая задача, N агентов × 1 изменение срока в секунду, окно 15 с, три прогона:

| Агентов | До: принято / потеряно | После: принято / отказ / потеряно | Значения и проекции после | p95 ответа до → после |
|---|---|---|---|---|
| 1 | 15 / 0 | 15 / 0 / 0 | сошлись | 26–29 → 38–41 мс |
| 2 | 30 / 0 | 30 / 0 / 0 | сошлись | 22–28 → 53–59 мс |
| 10 | 150 / 42–52 (28–35%) | 150 / 0 / 0 | сошлись | 36–58 → 216–230 мс |
| 50 | 750 / 309–344 (41–46%) | 574–581 / 0 / 0 | сошлись | 223–357 → 1954–2056 мс |

- «До» значения проекций совпадали с последним событием, но 28–46% принятых изменений событий не оставили.
- При 50 агентах «после» отправлено меньше: агент ждёт ответа, а одна задача обрабатывает около 38 изменений в
  секунду подряд, остальное стоит в очереди. Конфликтов версий в журнале API — 0 (до — 21 124 записи).
  Неизвестных исходов и отказов не было ни разу: ветки 409 и 503 проверены тестами, нагрузкой не вызваны.
- Цена потолка — по коду: каждое действие дважды перечитывает весь поток событий агрегата (загрузка и пересборка
  `tasks_read_model`); в профиле «пик» это 5 записей в секунду на все задачи, так что потолок одной задачи важен
  только для «стресса» в одну задачу.

Задержки по профилю, каждый агент в свою задачу, три прогона (90% сообщения, 10% статус):

| Режим | Сообщение p95 до → после | Статус p50 до → после | Статус p95 до → после |
|---|---|---|---|
| Пик: 50 агентов × 0,1/с, 60 с, 35 статусов | 18–21 → 18–21 мс | 14–15 → 24–26 мс | 19–20 → 35–36 мс |
| Стресс: 100 агентов × 1/с, 15 с, 152 статуса | 11 → 10–11 мс | 10–12 → 21–22 мс | 15–16 → 27–27 мс |

Сообщение не изменилось. Статус стал дольше на 10–16 мс: раньше ответ означал «сообщение с тегом сохранено», теперь
— «изменение зафиксировано и проекции обновлены».

Что изменилось для клиента:
- успех — 200 с `{"chat_id","version","replayed"}` вместо пустого тела (у `tasks/.../actions/*` было 204);
- новые ответы: 409 `CONCURRENT_MODIFICATION` значит «не применено», 503 `OUTCOME_UNKNOWN`, 422
  `IDEMPOTENCY_KEY_REUSED`, 403 для не участника чата (раньше так отвечала отправка сообщения), 422 вместо 500 для
  повторного закрытия;
- заголовок `Idempotency-Key`, до 200 символов, область — пользователь и чат;
- повтор того же значения больше не отвечает «готово» по возможно устаревшей проекции, а исполняется.

**Опыт с кэшем Mongo** (`--wiredTigerCacheSizeGB=0.25`, полный набор раздела 4 на бинаре базовой ветки, один
прогон, `docs/measurements/20261112-agentbench-cache025.jsonl`; `BENCH_MONGO_ARGS` в `run.sh`):

| После записей | 595–625 МБ, 57–59 тыс. сообщений | 482 МБ, 84 тыс. сообщений |

Задержки чтения при треде 2000 (p95 11–41 мс) и потолок записи хуже не стали, но фон машины в T-0012 был
выше (средняя загрузка 7–39 против 1–14), так что сравнение задержек слабое. Вывод: предел кэша снижает

не внесено: без бюджета памяти от владельца менять нечего, флаг остаётся параметром замера.
