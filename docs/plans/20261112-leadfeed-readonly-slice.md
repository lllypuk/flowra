# Первый срез: запуск без Keycloak и лента задач лида на чтение

Задача лида T-0008, 12.11.2026. Основание — `docs/agent-tracker-review.md` (ветка
`docs/agent-tracker-review`), раздел 4, пункт 6 с четырьмя условиями Codex.

## Overview

Flowra поднимается локально без Keycloak и показывает задачи лида лентой: список по «кого ждём» и тред
задачи. Источник — снимок из `lead-task`; Flowra его не толкует и ничего в него не пишет.

Рабочий канал не меняется: `lead-task` и почта agterm остаются единственным источником. Срез — параллельный
опыт: помогает ли тред делать четыре действия быстрее и правильнее, чем доска `lead-task` с поиском по
почте и транскриптам.

Что срез проверяет: локальный запуск и вход без Keycloak, достоверную проекцию задачи и треда, HTTP-чтение
с токеном, пользу такого вида. Чего не проверяет: запись агентов во Flowra, пригодность агрегата Chat под
задачи агентов, доступ с телефона, перенос источника правды.

## Context (from discovery)

- Журнал `~/projects/lead/tasks/events.jsonl` хранит только `new` (title, project, agent, cwd, sid, pane),
  `sent` (returned), `set` (status, note). Текстов писем и отчётов в нём нет; id событий нет
  (`lead-task`, `record()`).
- Статусы `work`, `question`, `review` и время `lead-task` досчитывает из транскриптов при каждом вызове
  (`build()`): поздно найденная запись меняет прошлые переходы. Отчёт распознаётся по Bash-команде с
  меткой — это не квитанция доставки. Реплика человека в сессии сдвигает `wait_user` у всех задач этой
  сессии — это не решение владельца.
- Записи транскрипта Claude Code несут `uuid`, вызовы инструментов — `id`: устойчивые ссылки на письмо и
  отчёт существуют.
- Вход: `TokenValidator` → `claims.ExternalUserID` → `UserResolver` находит или создаёт пользователя
  (`cmd/api/container.go:2327`). REST (`middleware.Auth`, `cmd/api/routes.go:25`) и HTML (`RequireAuth`,
  `cmd/api/container.go:890`) уже получают один валидатор и читают куку `flowra_session`.
- Без Keycloak сейчас открыто четыре пути: `StaticTokenValidator` пускает любой `dev-token-*`
  (`internal/middleware/auth.go:504`); веб-вход — `/auth/callback?code=mock-code` с кукой
  `mock-session-token` (`internal/handler/http/template_handler.go:482`); HTML без настроенного
  валидатора ставит mock-пользователя (`internal/handler/http/auth_middleware.go:93`);
  `/api/v1/auth/login` обслуживает `MockAuthService` (`cmd/api/container.go:1007`) и не проходит
  проверку токена. Сервер слушает `0.0.0.0:8080`.
- Загрузчик окружения заполняет только скалярные поля конфига, YAML переменные не раскрывает
  (`internal/config/config.go`): список токенов из окружения задать нельзя.
- Воркер без настроек Keycloak не стартует, если не задан `USER_SYNC_DISABLED` (`internal/worker/runner.go:155`).
- База на 12.11: сборка, `go vet`, интеграционные тесты зелёные. API-e2e — 5 падений: стенд создаёт
  `TaskHandler` без `TaskActionService` (`tests/e2e/setup_test.go:265`). `internal/infrastructure/eventbus`
  упал один раз в полном прогоне, в восьми отдельных прогонах с `-race` не воспроизвёлся; тесты ждут
  подписку `time.Sleep(100ms)` и ответ 2 с — гипотеза, не установленная причина.

## Solution Overview

Три независимые части.

1. **Вход по токену.** Режим `auth.mode: token`: именованные токены владельца, в конфиге только SHA-256
   случайных длинных секретов, сравнение за постоянное время. Все токены ведут на одного пользователя
   `owner`. API — `Authorization: Bearer`, веб — форма с токеном и кука HttpOnly. Отказ закрытый: в этом
   режиме нет отката на `StaticTokenValidator`, mock-пользователя и `MockAuthService`. Режим требует
   адреса loopback. Поведение режима Keycloak не меняется.
2. **Лента как отдельная проекция на чтение.** Свои коллекции, свой сервис, свои ручки. Импорт не
   проходит через агрегат Chat, обработчик тегов и маршруты действий — правка импортированного
   невозможна по построению, ADR-007 не затронут.
3. **Импорт полным снимком.** Скрипт сначала получает завершившийся успехом `lead-task export` во
   временный файл и только потом запускает `leadfeed import`. Импортёр складывает снимок в отдельное
   поколение, проверяет его и одним условным обновлением переключает активное поколение. Обрезанный,
   неполный или битый снимок оставляет прежний вид.

Отвергнуто:

- Импорт в агрегат Chat: у задачи три статуса, время событий стало бы временем импорта, запрет правки
  пришлось бы ставить во всех обработчиках и шаблонах.
- Разбор журнала и транскриптов самим проектором: два толкователя одних данных.
- Поток событий с курсором по времени: `build()` пересчитывает прошлое, поздняя запись со старым
  временем терялась бы. Дельта потребовала бы seq, исправлений и удалений, которых у `lead-task` нет.

## Technical Details

### Контракт снимка (нужен от лида)

JSONL, по объекту на строку, порядок: `header`, `task`…, `record`…, `footer`.

| Строка | Поля |
|---|---|
| `header` | `schema` (1), `source`, `epoch` (id установки журнала), `revision`, `as_of` (UTC), `derivation` (версия правил статусов), `complete`, `errors[]` |
| `task` | `id` (`T-0007`), `title`, `project`, `agent`, `created_at`, `status`, `waiting_on`, `status_since`, `note`, `returns`, `spent{queued,work,lead,user}`, `transitions[{at, status, cause, derived}]` |
| `record` | `id`, `task`, `kind`, `at`, `order`, `actor`, `actor_derived`, `source{kind, ref}`, `body`, `body_missing`, `format` |
| `footer` | `revision`, `tasks`, `records` |

- `record.kind`: `letter` (лид → агент: постановка, ответ, возврат), `report` (агент → лид), `decision`
  (`set` лида с заметкой), `observation` (наблюдение без текста, например реплика человека в сессии).
  Сообщение и переход — разные сущности: переход ссылается на запись через `cause`, письмо в треде одно.
- `id` записи устойчив между снимками: порядковый номер строки журнала в пределах `epoch`, `uuid` записи
  транскрипта, `id` вызова инструмента. Не время, не хэш текста, не индекс в отсортированном списке.
- Нет текста — `body_missing` с причиной, запись остаётся. Чужие результаты инструментов не выгружаются.
- `derived: true` и `actor_derived: true` помечают выведенное: реплика человека не объявляется решением
  владельца, обнаруженная команда отчёта — доставкой.
- Пути файловой системы, id сессий и панелей в снимок не входят.
- `waiting_on` и `spent` считает `lead-task`; Flowra их не пересчитывает.
- Экспортёр читает входы одним согласованным срезом; `as_of` — время этого среза, а не время печати.
- `complete: false` или непустой `errors` — снимок не публикуется. `body_missing` ошибкой не является.
- Тройка `source` + `epoch` + `revision` задаёт неизменяемый снимок: то же содержимое — повтор без
  последствий, иное содержимое под той же тройкой — отказ. Смена `epoch` принимается как новый источник
  и отмечается в состоянии.

### Контракт отображения статусов

Исходное значение хранится и отдаётся как есть; подпись и группа — только для показа.

| `status` | Подпись (как на доске `lead-task`) | `waiting_on` | Группа в списке |
|---|---|---|---|
| `queued` | в очереди | `agent` | у агента |
| `work` | в работе | `agent` | у агента |
| `question` | вопрос к лиду | `lead` | ждут лида |
| `review` | на проверке у лида | `lead` | ждут лида |
| `wait_user` | ждёт тебя | `owner` | ждут владельца |
| `done` | принята | — | закрытые |
| `cancelled` | отменена | — | закрытые |

Неизвестный статус показывается сырым значением в группе «неизвестно»; импорт не падает. В статусы Chat
ничего не отображается — потерь нет.

Часов три, и они не смешиваются: возраст статуса задачи (`status_since`), `as_of` снимка, время
последней удачной публикации. «Свежо» — только при удачной публикации полного снимка.

### Хранилище

- `leadfeed_tasks`, `leadfeed_records` — документы с полем `generation`. Поколение — локальный id одной
  попытки импорта; в опубликованное поколение никто не дописывает.
- `leadfeed_state` — один документ: активное поколение с его `source`, `epoch`, `revision`, `as_of`,
  счётчиками и хэшем содержимого; время и итог последней попытки; время последней удачи; текст
  последней ошибки; блокировка с владельцем и сроком.
- Публикация: запись нового поколения → проверка → одно обновление `leadfeed_state` с условием «блокировка
  всё ещё моя» → чистка. Импортёр, потерявший блокировку, не публикует, не чистит и чужую блокировку
  не снимает.
- Каждый импорт — пересборка с нуля: прежнее поколение читается до переключения.
- Чистка удаляет поколения, заменённые раньше срока удержания (больше таймаута ответа сервера).
- Один HTTP-ответ читает номер активного поколения один раз и берёт данные и метаданные только из него.
- Задача, отсутствующая в опубликованном снимке, из ленты исчезает; неполный снимок не публикуется.

### HTTP

Под `/api/v1/feed`, только `GET`, Bearer или кука:

- `GET /feed/status` — ревизия активного поколения, `as_of`, счётчики, последняя попытка, последняя ошибка.
- `GET /feed/tasks?waiting_on=&status=&limit=&cursor=` — список.
- `GET /feed/tasks/{id}` — задача с переходами.
- `GET /feed/tasks/{id}/records?limit=&cursor=` — тред, порядок `at`, `order`.

Каждый ответ несёт `revision` и `as_of`. Курсор привязан к ревизии: после смены ревизии — `409
FEED_REVISION_CHANGED`, клиент начинает сначала. Время — RFC 3339 UTC. Ошибки — существующий конверт
`{success, error{code, message}}`; 401 отличим от 404. Тело записи отдаётся текстом с полем `format`,
без исполнения и разметки.

Страницы `/feed` и `/feed/tasks/{id}` рендерятся из того же сервиса запросов, своих вычислений статусов
и времени в шаблонах нет.

## Телефон

Клиент для Android в срез не входит. Срез не проверяет доступ с телефона: `127.0.0.1` с него недостижим.

Чего нельзя делать в срезе, чтобы не мешать клиенту:

- **Вход.** Не привязывать вход к HTML-форме, куке, редиректам или HTMX: телефон шлёт Bearer напрямую.
  Токены именованные и отзываемые поодиночке — потерянный телефон отключается без смены остальных.
  Личность `owner` не зависит от токена и переживает его замену.
- **API.** Каждый экран ленты имеет JSON-ручку с тем же смыслом полей; HTML — потребитель того же
  сервиса. Идентификаторы — `T-0007` и id записей источника, не ObjectID Mongo, не пути, не id панелей
  agterm. Постраничная выдача ограничена и определена при смене ревизии.
- **Сеть.** Не открывать `0.0.0.0` молча и не вшивать `localhost` в ссылки и куки: базовый адрес
  настраивается, кука получает `Secure` под HTTPS. Токен не передаётся в строке запроса (так сейчас
  делает WebSocket, `internal/handler/websocket/handler.go:186` — ленте он не нужен).
- **Запись.** Ручек записи нет, но имена ресурсов чтения выбраны так, чтобы ответ владельца добавился
  без переименования.

Открытые вопросы, решать не в срезе:

1. Где живёт сервер. Ноутбук засыпает; журнал лида и транскрипты лежат на нём же. Перенос Flowra на
   постоянно включённую машину требует приёма снимка по сети.
2. Доступ вне домашней сети: частная сеть (WireGuard, Tailscale) или публичный адрес с HTTPS.
3. Уведомления: FCM, UnifiedPush/ntfy или Telegram. Срез даёт только опрос `GET /feed/status`.
4. Кто принимает ответ владельца, пока источник — журнал лида: Flowra не может писать в него.
5. Хранение токена на устройстве и срок его жизни.

## Критерий среза

Техническая готовность и живая оценка — два разных итога; первое не ждёт второго.

**Техническая готовность** (Task 11): импорт с нуля и повтор дают те же записи; обрезанный, битый и
пересекающийся импорт сохраняют прежний вид; статусы, переходы и покрытие текстами совпадают с
источником на той же ревизии; без токена и с неверным токеном — отказ; изменить импортированное
нельзя; журнал лида не тронут.

**Живая оценка.** Сравниваются доска `lead-task` вместе с обычным поиском по почте и транскриптам
против ленты Flowra, на одной ревизии данных.

- Когорта — десять настоящих задач лида, объявленная заранее, начиная с первого полного снимка.
  На 12.11 в журнале восемь задач (одна учебная, четыре ретро, SkyV Arc, две Flowra): недостающие
  добираются естественным потоком. Желательны разные проекты, вопрос с `wait_user`, возврат с
  проверки, приёмка, длинный тред; чего не случилось — названо, события ради оценки не создаются.
- Четыре действия на каждой применимой задаче:

  | Действие | Правильный ответ |
  |---|---|
  | Найти последнее принятое решение | решение, автор, область, время, ссылка на источник; если не записано — «явного решения нет» |
  | Понять, кто блокирует шаг | статус и `waiting_on` на ревизии, заметка или вопрос; выведенное помечено |
  | Восстановить задачу после перезапуска | поручение, состояние, последний отчёт, следующий записанный шаг; если шага нет — «нет данных» |
  | Проверить сданный результат | отчёт, его проверки и ссылки, приёмка или возврат; сдано ≠ принято |

- Ключ ответов составляется по первоисточнику до опыта; Flowra себе не судья.
- Порядок видов чередуется, чтобы не мерить память.
- На попытку пишутся: правильность по ключу, время до ответа, число переходов между источниками,
  помощь и повторные вопросы, устаревшие и отсутствующие данные. Предел времени задаётся заранее,
  превышение считается.
- Нет свидетельства в источнике — пробел покрытия; есть в источнике, нет во Flowra — дефект импорта.
  Неудачи из выборки не выбрасываются.
- Отчёт — парные разности и размер выборки, без заявлений о значимости. Отдельной строкой — цена
  обслуживания зеркала: сбои импорта, пересборки, правки контракта.

Провал `lead-task` для продолжения не требуется; красивая лента не основание для переноса источника.
